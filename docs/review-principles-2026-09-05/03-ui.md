# UI – 5 September 2026 review

## Verdict

The UI layer is disciplined where it matters. Nothing under `src/components`, `src/composables`,
`src/App.vue` or `src/prologue` bypasses the store facade (one grep, zero hits), nothing mutates a
snapshot locally, no computed has a side effect, no prop is destructured, and the lifecycle
inventory is 19 rows with one harmless gap. Templates carry no Cyrillic, every icon-only control has
a name, the responsive wave landed on the owner's ladder with zero `!important` and zero unused
classes in the three biggest screens. The mounted net is real: 124 files, and the four largest
components are each covered by 13–27 of them.

Three things matter most. First, a career that refuses to load at boot – a schema-newer save is the
realistic case – drops the player into the childhood prologue with their careers intact but hidden
and no message (U-01, reproduced). Second, the store's own recovery sentences ("Simulation restarted
from the last saved week", "outdated screen – refreshed") have no surface on nine screens and
overlays, so a refused command on Money, Calendar or the Kid screen is a silent nothing (U-02,
reproduced). Third, two screens rebuild the coach's weekly bill from `seed` through three engine
calls, and the comment in one of them records that the last clock bug had to be fixed in each copy
separately – the snapshot should carry the fact (U-03).

### U-01 – A refused boot load opens the prologue over intact careers

**What.** `init()` (`game.ts:144–176`) probes `listCareers` directly so that a storage failure lands in
`phase = 'recovery'` – the comment at 151–156 says why: the old code "booted a player with years of
careers straight into the onboarding wizard". But the next step, `await this.loadCareer(mostRecent.careerId)`
(166), goes through `runOp` → `run` (`596–603`, `190–225`), and `run` catches every refusal, writes
`this.error` and returns `undefined` (221). `init` then continues to `this.ready = true; this.phase = 'ready'`
(168–169) with `snapshot === null`. `App.vue:298` defines `showOnboarding = game.ready && !game.snapshot`,
the watcher at 320 routes that to `newGameRoute = 'prologue'`, and 1528–1534 render `ChildhoodPrologue`
– which, like `PrologueCard`, `PrologueLocalOpen` and `PrologueHandover`, renders neither `game.error`
nor `saveOp` (grep: zero hits in the four files).

The realistic trigger is a save newer than the build: `engine/migrations.ts:2365–2366` throws
`Save schema N is newer than supported M`, which reaches the store as a typed refusal. Reproduced
with a scripted worker (`rv36-U/probe-boot-newer-schema.log`, exit 0):

```
requests: ["listCareers","loadCareer"]   phase: "ready"   ready: true   snapshot: null
careersKept: 1   error: "Save schema 71 is newer than supported 70"   initError: ""
saveOp: {op:"load", status:"error", message:"Save schema 71 is newer than supported 70"}
App.vue:298 showOnboarding: true
```

**Why it matters.** It is the exact failure the init comment declares fixed, reopened through the
other exit. The player sees a new-child story; the careers list is still on disk and still in
`store.careers`, but no surface says so, and the one message that explains it sits in `game.error`
and `saveOp`, which only `More` renders – a screen that is not reachable while the prologue is up.
"Start a new career" is what the recovery screen offers as an explicit choice; here it is the
default outcome.

**Proposed response.** In `init`, treat a refused boot load as a recovery exit: after
`await this.loadCareer(...)`, `if (!this.snapshot) { this.initError = this.error || 'The most recent career could not be loaded'; this.phase = 'recovery'; return }`
– or give `loadCareer` a `{ rethrow: true }` path used only from `init`. The recovery screen
(`App.vue:1499–1518`) already renders `initError` verbatim, keeps Retry / Import / Start new, and
never deletes anything. The probe file above is the test: move it to `tests/` and flip its
expectations to `phase === 'recovery'`, `initError` set, `showOnboarding === false`. Wording: the
recovery heading "Saved games can't be reached" and its hint speak of storage; whether they fit a
schema-newer save is the owner's call – report it with the change, do not reword.

**Risk of the response.** Low. The only behaviour that changes is a boot that today silently starts a
prologue; every other exit of `init` is untouched, and `startFreshFromRecovery` (186–189) is the
same explicit door the IndexedDB case already has.

### U-02 – The store's recovery sentences have no home on nine surfaces

**What.** `run()` writes four player-facing sentences into `this.error`: SAVE_CONFLICT (218), a
generic refusal (221), the restart line (241) and the stale-screen line (256). `game.error` is
rendered by exactly five templates – `OnboardingWizard.vue:671`, `SeasonScreen.vue:1357`,
`MoreScreen.vue:641`, `CoachMarketScreen.vue:661`, `HomeScreen.vue:1166` – and by nothing in the App
shell (`App.vue:1505` and 1512 render `initError` and an import failure only). `MoneyScreen`,
`CalendarScreen`, `KidScreen`, `ThisWeekScreen`, `TournamentFlow`, `PlanWeekSheet`, `InboxSheet`,
`OfferLetter` and `ForkDialog` have no `class="error"` element at all (grep of each template).
`MoneyScreen`'s script mentions `error` nowhere. Reproduced by mounting each screen with a fixture
snapshot and setting `store.error` (`rv36-U/probe-error-surface.log`, exit 0):

```
HomeScreen: true   MoneyScreen: false   CalendarScreen: false   KidScreen: false   ThisWeekScreen: false
```

Traced end to end for one refusal: `MoneyScreen.vue:1418–1422` `confirmShop` → `game.buyAsset`
(`game.ts:419–425`) → worker → `engine/world/shop.ts:358` throws `Not enough funds for that` →
`sim.worker.ts:650` `errorMsg` → `game.ts:119` `takeOk` throws `CommandRejected` → `run` catch writes
`this.error` (221) → the Money screen renders nothing and `run` clears `error` on the next command
(192). The affordability half is pre-checked by `canBuy` (`MoneyScreen.vue:1051–1059`) and by
`fundsShort` on Season and Calendar, so the money refusals are normally unreachable; the lines that
are reachable from any screen are the integrity ones – another tab committed, the worker restarted,
the screen was stale – and those are precisely the ones the store writes for the player to read.

**Why it matters.** W1-INTEGRITY-A and TB-05 exist so that "nothing happened" is always explained.
On more than half the app it is not, and the explanation is overwritten by the next tap.

**Proposed response.** Render `game.error` once, in the shell: a `<p class="error" role="status">`
in `App.vue`'s frame directly under the two top notices (near 1577), and delete the five per-screen
copies in the same change so no screen shows it twice. The probe above becomes the mounted test
(App mounted with a fixture snapshot, `store.error` set, text contains the sentence on every tab).
`fits.ts` already has `assertRowFits` for the notice band at 375. Wording: none – the sentences are
the store's existing ones. If the shell placement collides with the sticky bar's box, that is a
layout question for the owner's design pack, not a copy question.

**Risk of the response.** Medium-low: the notice band's height moves the content below it on every
screen when an error is showing, which `tests/component/fits.ts` measures; run the 27 App-mounting
files after the change.

### U-03 – The coach's weekly bill is rebuilt from `seed` in two screens

**What.** `MoneyScreen.vue:272–283` and `ThisWeekScreen.vue:218–221` run the same chain:
`ageAtWeek(snap.week)` → `coachById(snap.seed, age, snap.coachId)` → `tierOf` / `facilityRateCents`
→ `coachBillRangeCents(rate, snap.plan, snap.profile.background)` (Money also `weeklyBillSplit`).
`coachById` regenerates the coach market from the seed on the UI thread. The comment at
`MoneyScreen.vue:262–271` records that the age-clock bug ("a December girl is 16 from week 156 to
week 204 while the market had restocked at 17") was "measured on the identical bug one screen over"
– fixed twice, once per copy. `snapshot.ts:350–372` already projects `coachBilling` with
`weeklyCents`, `seasonCents`, `travelFareCents`, but no range and no split.

This is the sharpest case of a wider pattern: `rv36-U/engine-value-imports.txt` lists 123 value
imports from `src/engine` into the UI. Most are shared vocabulary (`TIERS`, `ECONOMY`, `KID_ID`,
labels) or pure previews of a local draft (`HerWeekTab.vue:74–101` needs `planWeek`/`resolveWeek` to
show a plan the engine has not seen yet – legitimate). The ones that re-evaluate an engine RATE
against snapshot state are the candidates: this pair, `kidPrizeShareBps(ageYears)`
(`MoneyScreen.vue:187`), `managerCommissionBps()` (199), `prizeCentsFor` (`TournamentFlow.vue`,
`NextTournamentPanel.vue`). The duplication lane counts the clones; the judgement here is that a
rate the engine bills at belongs on the snapshot the moment two screens quote it.

**Why it matters.** Each copy is a place the bill can drift from the charge, and the recorded
history says it did. `coachById` on the main thread is also the one engine generator the UI runs
per render of two screens.

**Proposed response.** Add `weekRangeCents: [number, number]` and `split: { coachCents, facilityCents, totalCents }`
to `Snapshot['coachBilling']`, computed engine-side from the same `coachBillRangeCents` /
`weeklyBillSplit` the till uses; both screens read the fields and drop the imports of `coachById`,
`tierOf`, `facilityRateCents`, `coachBillRangeCents`, `weeklyBillSplit`. Mounted tests: Money's
"Yours runs $lo–$hi" sentence (already asserted in `tests/component/bills-sponsor-quota.test.ts`
family) and ThisWeek's estimate, both against the snapshot field rather than a recomputation.
`Snapshot` is a projection, not the save – no `SAVE_SCHEMA_VERSION` move. Wording: none.

**Risk of the response.** Low. The formatting stays; only the source of the numbers moves. The
December-girl case needs a fixture assertion so the engine-side computation uses the market's clock
(`ageAtWeek`) and not `ageYears`, exactly as the comment demands.

### U-05 – The splash pulse ignores reduced motion; one predicate, three copies

**What.** `src/style.css` declares four real animations: `.splash-logo` (1497) and `.splash-hint-wrap`
(1512) fade once, `.splash-hint` (1521) pulses `1.8s ease-in-out infinite`, `.trophy-flight` (3736).
Its only `prefers-reduced-motion` block (4349–4354) covers `.cm-switch`. The trophy flight is
guarded in script (`trophyArrival.ts:151` refuses to arm); the day-cross sweep likewise
(`dayCross.ts:187`); every one of the three components that animates carries its own reduce block
(`ConfettiBurst`, `ProgressRing`, plus the screens listed in `rv36-U/media-locations.txt`). The
splash pulse has neither. `prefersReducedMotion()` is written three times: `dayCross.ts:172–175`,
`trophyArrival.ts:135–138`, and inline in `weekPager.ts:210–211`.

**Why it matters.** The first thing a player who has asked for less motion sees is the one element
that never stops moving. Small, and the one gap in an otherwise complete policy.

**Proposed response.** One rule in style.css: `@media (prefers-reduced-motion: reduce) { .splash-hint { animation: none } }`,
next to the `.cm-switch` block. Move `prefersReducedMotion` to one composable (`dayCross.ts` already
exports it) and import it in the other two. Test: the e2e layer can `emulateMedia({ reducedMotion: 'reduce' })`
and read `animation-name` on `.splash-hint`; happy-dom cannot evaluate media queries, so a mounted
assertion here would be a source pin – declare it as "policy" per QA-38 if used.

**Risk of the response.** None to behaviour; the splash still fades in.

### U-06 – One popup outside the focus-managed set

**What.** `useDialogFocus` is called by thirteen components (Birthday, CollegeDone, Confirm, Fork,
InjuryStop, Knock, PrologueCard, SeasonSummary, ShootClash, WeekSpanReport, PrologueHandover,
Retirement, TourBriefing). `RankHelpDialog.vue:44–46` is a `.dialog-overlay` scrim with a
`.guide-card`, a named close button and a backdrop click – no `role="dialog"`, no `aria-modal`, no
focus entry or trap, no Escape. `EndingScreen.vue:148` has `role="dialog" aria-modal="true" aria-label="Epilogue"`
and no `useDialogFocus`. The three sheets (`InboxSheet`, `PlanWeekSheet`, `OfferLetter`) are
full-screen takeovers with a header close, by the app's own rule (`PlanWeekSheet.vue:266–274`), and
are not dialogs.

**Why it matters.** `dialogFocus.ts:9–13` states the argument: `aria-modal` without containment is
worse than neither. RankHelp has neither, so Tab walks behind it; the epilogue announces modality
and then lets the keyboard leave.

**Proposed response.** RankHelp: `role="dialog" aria-modal="true" aria-labelledby` on the
`.guide-title`, `tabindex="-1"` on the card, `useDialogFocus(card, () => emit('close'))`. Ending:
`useDialogFocus(root)` with no Escape (it is a blocking takeover, like the knock). Test: the three
`a11y-sweep.test.ts` cases at 172–206 (focus lands, Tab wraps, Escape policy), applied to both.
`RankHelpDialog` is also the one dialog with no `assertDismissReachable` net – add it while there.
Wording: none.

**Risk of the response.** None.

### U-07 – Home reads `localStorage` unguarded at setup (unverified, by reading only)

**What.** `HomeScreen.vue:117` `const showKidHint = ref(!localStorage.getItem(KID_HINT_KEY))` runs
in `<script setup>`, and 121 writes it. Eighteen files touch `localStorage`; the composables wrap
every access in `try/catch` (`inboxCue.ts:178–189`, `matchDefaults.ts`, `dayCross.ts`,
`weekRecap.ts`, `sfx.ts`, `haptics.ts`, `music.ts`), and these two lines are the only bare accesses
left in a component (`App.vue`'s mentions are comments). There is no shared safe-storage helper.
The repo's own mounted tests document the sensitivity: `a11y-sweep.test.ts:58–61` shims
`localStorage` because "HomeScreen READS IT AT SETUP".

**Why it matters.** Browsers that block site data throw `SecurityError` on the property access
itself; Home is the first screen of every career. Not reproduced in a browser here.

**Proposed response.** A ten-line `src/composables/localStore.ts` (`readLocal(key)`, `writeLocal(key, value)`,
both swallowing) used by these two lines; the composables can migrate on touch. Mounted test:
define `localStorage` as a throwing getter, mount `HomeScreen`, assert it renders the hero.

**Risk of the response.** None.

### U-08 – Two timers without a teardown

**What.** `MoreScreen.vue:122–124` `okTimer` is cleared only when the next `saveOp` arrives;
`303` `setTimeout(() => (seedCopied.value = false), 1500)` is never cleared. Neither has
`onBeforeUnmount`. Every other component timer does (`ConfettiBurst.vue:122–123`,
`dayCrossSweep.ts:125`, `playbackClock.ts:207–209`).

**Why it matters.** Harmless today – a ref write after unmount is a no-op – but it is the one
inconsistency in a 19-row lifecycle table, and the pattern spreads by copy.

**Proposed response.** `onBeforeUnmount(() => { clearTimeout(okTimer); clearTimeout(copyTimer) })`
with `copyTimer` held like `okTimer`. Test: fake timers, unmount, advance, assert no throw and no
write – or simply accept the symmetry without a test.

**Risk of the response.** None.
